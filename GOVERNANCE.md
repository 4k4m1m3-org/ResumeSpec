# Governance

## Overview

ResumeSpec is an open specification project focused on creating a transparent, collaborative, and community-driven standard for structured resumes and professional profiles.

This document describes the governance model used to guide the evolution of the project, including decision-making processes, roles, responsibilities, and contribution paths.

The goal of this governance model is to ensure that ResumeSpec evolves in a predictable, inclusive, and technically sound manner.

---

# Project Principles

ResumeSpec governance is based on the following principles:

- Openness: Decisions should be transparent and accessible to the community.
- Collaboration: Improvements should be developed through discussion and shared knowledge.
- Technical quality: Decisions should prioritize maintainability, compatibility, and long-term value.
- Stability: Changes should consider existing users and implementations.
- Inclusiveness: Different perspectives and experiences are valuable.
- Documentation: Important decisions should be recorded and explained.

---

# Project Roles

## Maintainers

Maintainers are responsible for the overall health and direction of the project.

Responsibilities include:

- Reviewing contributions.
- Maintaining project standards.
- Managing releases.
- Reviewing RFC proposals.
- Ensuring documentation quality.
- Facilitating technical discussions.
- Protecting the project's long-term vision.

Maintainers do not own the specification; they serve the community by helping coordinate its evolution.

---

## Contributors

Contributors are community members who participate in improving ResumeSpec.

Contributions may include:

- Code improvements.
- Documentation updates.
- Specification proposals.
- Testing.
- Examples.
- Reviews and feedback.

All contributors are encouraged to participate constructively in project discussions.

---

## Reviewers

Reviewers help evaluate contributions before they are integrated.

Responsibilities include:

- Reviewing pull requests.
- Providing technical feedback.
- Identifying potential issues.
- Helping maintain quality standards.

Reviewers may be invited based on their experience and contributions to the project.

---

# Decision Making

ResumeSpec follows a consensus-oriented decision-making process.

Decisions should generally follow this approach:

1. Discussion and proposal.
2. Review of technical considerations.
3. Community feedback.
4. Maintainer evaluation.
5. Final decision and documentation.

The objective is not to eliminate disagreement, but to reach decisions that best serve the project's long-term goals.

---

# Specification Governance

Changes to the ResumeSpec specification should follow the RFC process.

Examples of changes requiring an RFC:

- Adding new sections.
- Changing existing structures.
- Modifying compatibility rules.
- Introducing breaking changes.
- Defining new standard behaviors.

RFCs provide a structured way to:

- Explain the motivation.
- Evaluate alternatives.
- Collect feedback.
- Document decisions.

---

# RFC Lifecycle

A typical RFC lifecycle includes:

## Proposal

The author creates an RFC describing the proposed change.

---

## Discussion

The community reviews the proposal and provides feedback.

---

## Review

Maintainers evaluate:

- Technical impact.
- Compatibility concerns.
- Implementation feasibility.
- Alignment with project goals.

---

## Decision

The RFC may be:

- Accepted.
- Rejected.
- Deferred.
- Returned for revision.

---

## Implementation

Accepted RFCs may be implemented through:

- Specification updates.
- Reference implementations.
- Documentation changes.
- Tooling improvements.

---

# Release Management

Project releases should aim to provide:

- Clear versioning.
- Documented changes.
- Migration information when required.
- Compatibility considerations.

Release decisions are managed by maintainers following the project's versioning strategy.

---

# Breaking Changes

Breaking changes should be carefully evaluated.

Before introducing breaking changes, maintainers should consider:

- Existing implementations.
- User impact.
- Migration complexity.
- Long-term benefits.

Breaking changes should be documented clearly and communicated before adoption.

---

# Community Participation

Everyone participating in ResumeSpec is encouraged to:

- Share ideas.
- Review proposals.
- Report issues.
- Provide constructive feedback.
- Help improve documentation.

Participation does not require formal membership or approval.

---

# Conflict Resolution

Technical disagreements are expected in an open source project.

When conflicts arise:

1. Participants should discuss technical concerns respectfully.
2. Arguments should focus on evidence and project goals.
3. Maintainers may help facilitate discussions.
4. Final decisions should be documented when significant.

Personal attacks or unproductive discussions are not acceptable.

---

# Transparency

Important project decisions should be documented through:

- RFCs.
- Issues.
- Pull requests.
- Release notes.
- Documentation updates.

The project aims to make its evolution understandable for both current and future contributors.

---

# Future Evolution

As ResumeSpec grows, this governance model may evolve to support:

- Additional maintainers.
- Working groups.
- Community representatives.
- Formal specification committees.

Changes to governance should themselves be discussed transparently with the community.
